# 课题五路由接口速查

面向课题五外部路由服务开发者。本系统负责工单、容器部署、业务执行和结果评估；路由服务负责选择计算节点/GPU、计算业务路径并回写结果。

完整字段、SQL 参考和异常处理见 [外部路由系统完整对接说明](integration-guide.md)。

## 1. 服务地址

验收管理网：

```text
平台后端：http://172.16.0.254:8181
平台前端：http://172.16.0.254:8182
```

路由服务若部署在管理节点，可使用 `http://127.0.0.1:8181` 访问平台后端。

联调前，管理员应在系统设置中将“业务测评路由”切换为“外部路由系统”。内部自动路由仅用于平台自测，不会替外部路由服务领取工单。

## 2. 最小循环

```text
GET pending 工单
 -> PATCH claim
 -> 查询节点、基线和本地 GPU 占用
 -> 选择 compute 节点、GPU 与路径
 -> POST result 回写 placement
 -> 下发网络规则后 POST network-ready
 -> 查询 release 事件并 ack
```

每个工单使用 `task_orders.id` 作为唯一 ID；它等于 `routing_input_dag.job_id`、`routing_input_dag.order_id` 和接口中的 `order_id`。

## 3. 必要接口

| 用途 | 方法和路径 | 说明 |
|---|---|---|
| 获取待路由工单 | `GET /api/routing-orders?status=pending&limit=100` | 读取工单和 `routing_input_dag`。 |
| 领取工单 | `PATCH /api/routing-orders/{order_id}/claim` | 必须先领取；并发下只有一个调用会成功。 |
| 查询拓扑节点 | `GET /api/nodes` | 使用 `hostname`、`node_kind`、`is_schedulable`、`is_routable`、`gpu_count` 和业务面地址。 |
| 查询任务基线 | `GET /api/baselines?task_type={task_type}` | 返回 `node_hostname`、`metric_key`、`baseline_value`、`operator`、`stable` 等。 |
| 回写路由结果 | `POST /api/routing-orders/{order_id}/result` | 回写 compute/GPU/path，平台物化实例并返回网络绑定。 |
| 确认网络就绪 | `POST /api/routing-orders/{order_id}/network-ready` | 流表、QoS 或路径规则下发完成后调用。 |
| 查询资源释放 | `GET /api/routing-resource-events?event_type=release&unacked=true&limit=100` | 将释放的 GPU 放回路由服务资源池。 |
| 确认释放已处理 | `POST /api/routing-resource-events/ack` | 对已处理的 release 事件回写确认。 |

当前上述接口用于内部联调，查询和路由接口不要求额外 service token。路由服务应为 `/result` 设置至少 60 秒、推荐 120 秒 HTTP 超时；超时后先查询工单状态，避免重复扣减 GPU。

## 4. 节点和基线选择

### 4.1 候选计算节点

只从下列节点选择 compute placement：

```text
node_kind = worker
is_schedulable = true
is_routable = true
hostname in compute-1, compute-2, compute-3
```

`source`、`sink` 通常是 `h1` 至 `h13` 终端节点。工单是否需要平台部署 source/sink，由 `runtime_config.platform_deployment.deployable_roles` 决定，路由服务不需要决定容器部署。

### 4.2 基线接口的使用

以视频 AI 推理为例：

```http
GET /api/baselines?task_type=low_latency_video_pipeline
```

路由服务应将返回的 `node_hostname` 与 `/api/nodes` 的 `hostname` 对齐，不要用 `node_id` 回写 placement。

| 任务类型 | 推荐 `metric_key` | 排序方向 |
|---|---|---|
| `low_latency_video_pipeline` | `frame_latency_p90_ms` | 数值越小越好 |
| `high_throughput_matmul` | `effective_gflops` | 数值越大越好 |

### 4.3 课题五低时延转发要求

当 `routing_strategy=low_latency_forwarding`，且工单包含需要部署的 `compute` 角色时：

1. 过滤可调度、可路由且存在空闲 GPU 的计算节点。
2. 查询本工单 `task_type` 的基线；时延类任务必须使用时延指标，例如视频 AI 的 `frame_latency_p90_ms`。
3. 优先选择 `stable=true` 的节点，并按 `baseline_value` 升序选择最低值。
4. 若最低基线并列或差异不显著，再以端到端网络时延、跳数和链路稳定性决定路径。
5. 选择该节点未被占用的 `gpu_device`，并在回写中声明。
6. 若没有可用的稳定时延基线或 GPU，调用 requeue 或等待下一轮；不得把同一 `hostname + gpu_device` 分给两个未释放任务。

这项规则只适用于时延类任务。矩阵乘法的吞吐基线方向相反，不能按最低值选择。

## 5. 回写格式

`placements[].topology_node_id` 必须使用 `nodes.hostname`，例如 `compute-3`，不能使用数据库 `node_id` 或资产拓扑 ID。

```json
{
  "strategy": "low_latency_forwarding",
  "placements": [
    {"task_node_id": "source", "topology_node_id": "h1"},
    {"task_node_id": "compute", "topology_node_id": "compute-3", "gpu_device": "1"},
    {"task_node_id": "sink", "topology_node_id": "h2"}
  ],
  "metadata": {
    "selected_reason": "compute-3 GPU 1 is free; frame_latency_p90_ms is the lowest stable candidate baseline",
    "path": ["h1", "compute-3", "h2"],
    "router_version": "topic5-router-v1"
  }
}
```

平台将 `gpu_device` 写入实例节点、容器环境变量 `GPU_DEVICE` 和 Docker GPU DeviceRequest。工单详情可展示所选节点、GPU、业务面地址和路由解释。

## 6. 网络确认和 GPU 释放

`POST /result` 成功只代表 placement 已保存且实例已物化。路由服务完成真实流表/QoS/路径规则下发后，调用：

```http
POST /api/routing-orders/{order_id}/network-ready
```

平台停止、删除或测评清理任务后，会写入 `routing_resource_events` 的 `release` 事件。路由服务按 `node_hostname + resource_id` 释放本地 GPU 占用，再调用 ack。`router_ack_at` 非空表示平台已记录路由侧确认。

## 7. 最小联调验收

1. 管理员切换为“外部路由系统”，创建 3 条同一任务类型工单。
2. 路由服务领取工单，读取 `/api/nodes` 和 `/api/baselines`。
3. 为每条工单选择不同的空闲 GPU，回写 placement。
4. 下发网络规则后调用 `network-ready`。
5. 平台前端确认工单显示已分配、compute 节点和 GPU。
6. 删除其中一条任务，读取 release 事件并 ack，确认该 GPU 可被下一条工单重新使用。
